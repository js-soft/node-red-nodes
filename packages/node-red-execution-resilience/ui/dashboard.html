Securing the Dashboard

This dashboard shows recorded message payloads - potentially PII, secrets, or other sensitive business data - not just flow structure. That's a meaningfully more sensitive surface than the Node-RED editor itself, and it is served on its own, separate from Node-RED's own adminAuth - configuring adminAuth for the editor does not also protect this dashboard. Left unconfigured, anyone who can reach the Node-RED HTTP port can browse full execution history with no login at all - the orange banner at the top of every page whenever that's the case exists precisely so this never happens silently.

Set execHistoryAuth in settings.js to require HTTP Basic Auth (the browser's native login prompt - no separate session/cookie mechanism to manage) for the whole dashboard surface, pages and API alike:

execHistoryAuth: { username: 'admin', password: '$2b$08$...' // a bcrypt hash - never plaintext }

Generate the hash exactly like you would for Node-RED's own adminAuth - this uses the same bcryptjs library and hash format, so a hash you already generated for adminAuth works here too: node-red admin hash-pw, or without the Node-RED CLI: node -e "console.log(require('bcryptjs').hashSync('yourpassword', 8))".

The editor's own "Execution Resilience" sidebar tab shows a live system health overview (stat counts, recent executions) without opening this dashboard at all - it never attempts an authenticated fetch itself, since that would trigger the browser's native Basic Auth prompt just from opening the editor. When execHistoryAuth is configured, it shows a "Protected - open the dashboard to sign in" note instead of live data.

How tracking works

Every inject and http in node is treated as a flow origin - the moment one fires, a unique execution id is generated and stamped onto msg._executionId. No node needs to be placed anywhere for this to happen; it's done by global hooks (onSend, onComplete) registered once for the whole runtime, not by an instance of any node this package ships.

From there, every node in the flow gets exactly one message recorded automatically: the origin gets one input entry (its outgoing payload - what starts everything), and every node after that gets one output entry, recorded when it calls its done() callback. No node needs to be placed anywhere for this - the only node this package still offers, Mark Execution Complete, exists purely to flag when a flow with no http response node is actually done (see below), not to enable tracking itself.

When is an execution marked COMPLETED?

There isn't a universal "the flow is done" signal in Node-RED, so this node uses the one terminal point most HTTP flows actually have: an http response node. When one completes, its output is flagged isResult: true and the whole execution flips to COMPLETED. Most non-HTTP flows have no equivalent, so this package ships a dedicated execution-complete ("Mark Execution Complete") node that does the exact same thing on purpose - drop it wherever a flow actually ends and it flips to COMPLETED too, flagged isResult: true just like an http response node would be.

StatusMeaningTrigger
RUNNINGExecution in progressAn inject/http in node fires
COMPLETEDSuccessfully finishedAn http response node completes, or a Mark Execution Complete node is reached
FAILEDError occurredAny node calls its done(err) callback with an error

Two consequences worth knowing. First: a flow with no http response node and no Mark Execution Complete node placed anywhere stays RUNNING forever as far as this feature is concerned - that's expected, not a bug; there's simply no terminal signal for it to observe.

Second, FAILED detection has a real blind spot worth knowing about. It's wired up via the same runtime hook (onComplete) used for everything else, which fires whenever a node calls done(err) - the same mechanism behind Node-RED's own Catch node, so this catches the same failures a Catch node would. It does not, however, catch a node that throws synchronously inside its own input handler (Node-RED routes that straight to the node's error log without ever calling done()), nor a node that simply hangs and never calls done() at all. Both of those leave the execution stuck RUNNING rather than flipping to FAILED - a limitation of Node-RED's hook API, not something this node works around.

Why the message tree is structured the way it is

The dashboard doesn't show messages as a flat, timestamp-ordered list. Instead it replays the actual wiring of the flow: every node's send() call is also recorded as an edge (source node/port → destination node), and the detail view reconstructs a tree from those edges rooted at the origin's one input message. That's what makes it possible to render a genuine branch structure - "Output 1 - next-node-name", "Output 2 - other-node-name" - rather than interleaving two unrelated branches' messages together just because they happened close in time.

Only the branch leading to the first isResult-flagged message (typically the path to an http response) auto-expands; sibling branches start collapsed, since that's usually the outcome you actually care about. If no isResult message exists anywhere (most non-HTTP flows), every branch defaults to expanded instead - there's no principled way to prefer one over another.

A node that ran more than once for the same execution - a Split node, and everything downstream of it until the matching Join - is rendered as one box tagged split with ←/→ arrows to step through each part, rather than one box per part. Once a Join recombines the parts, downstream nodes automatically go back to a single box each - nothing to configure.

When one output is wired to several destination nodes (not a Split - just multiple wires off one port), each destination gets its own nested, independently collapsible sub-branch inside that output's box - as long as they never reconverge. Whether they do is checked by comparing each destination's full downstream reachable set (everything reachable by following recorded edges forward): if any node is reachable from more than one of them, they're not independent stories - they're a "diamond" that merges back together - so they're deliberately left flat, one after another with no sub-branch chrome, exactly like a single destination would be. Splitting a reconverging pair into two separate dropdowns would misrepresent a shared continuation as two unrelated ones (and, depending on where they merge, would either duplicate or arbitrarily assign the shared portion to just one of the two).

Known limitation: hand-rolled message fan-out

Tracking is carried entirely by the msg._executionId property. Node-RED does not copy custom properties onto message objects you construct yourself, so a node that fans a single input out into several new messages can silently drop tracking for everything past that point - not because of a bug in this node, but because there's nothing on the new message tying it back to the execution.

A common case - a node that node.send()s several times in a synchronous loop, e.g. msg.payload.forEach(item => node.send({ payload: item })) - is handled automatically: the tracker temporarily remembers "this node is currently processing execution X" for exactly the duration of that synchronous call, so sends made from inside it inherit the id even though they never carried it explicitly.

This can only ever cover work that finishes before the node's input handler returns, though. If part of the fan-out is asynchronous - for example, you have a list of URLs and fire off a fetch() per URL, sending each result whenever it resolves later - those sends happen after the synchronous window has already closed, often after the node has already called done(). At that point there's no way to reliably attribute the send to one execution over another (two unrelated messages could be mid-flight on the same node at once), so those results won't be tracked.

Workaround: keep the fan-out and the async work in separate nodes, one URL per message, rather than doing both inside one loop:

  1. Split the list into individual messages synchronously first - either with Node-RED's built-in Split node, or a simple forEach + node.send() loop (now covered by the fallback above).
  2. Do the actual fetch() in the next node, one call per incoming message - and build the outgoing message by mutating or cloning the one you received, not a bare new object:
// fetch-one-url node - one message in, one async call, one message out
fetch(msg.url).then(result => {
  msg.payload = result;   // reuse the SAME message object
  send(msg);
  done();
});

Because each URL is its own message from the start, _executionId travels with it the ordinary way Node-RED already handles message properties - no fallback needed, and no ambiguity about which async result belongs to which execution.

Replay

Every row on the Executions tab has a ↻ (Replay) icon that resumes it - typically a FAILED execution, after fixing whatever caused it - as a brand-new, separately tracked execution. Every execution can always be replayed as a full Restart from Origin, re-running the whole flow from the beginning with its original input - that's the default, always-available option, no node placement required. Executions produced by a replay are tagged with a replay badge and a subtle tint in the list, and the Replays stat card filters the list down to just them (combine it with a status filter for e.g. "failed replays").

A full restart isn't always the right choice, though: if the original execution already wrote to a database, charged a payment, or sent a notification before it failed, restarting from scratch would repeat that side effect. That's what Mark Replay Point - the one node this feature adds to the package, sharing Mark Execution Complete's color since both are the same kind of thing: a deliberately-placed marker, not a message transform - is for: an additional, optional resume point that skips everything before it. Where that node belongs in a flow is a judgment call about side effects that only the flow's author can make, so this package deliberately doesn't try to infer it automatically (e.g. by detecting "was a database call made yet?"). Placing the node forces that choice to be explicit and visible in the flow itself, rather than the dashboard silently guessing whether a restart is safe. Its name is required (not just cosmetic, like Mark Execution Complete's) since it's how the checkpoint picker below and a replayed execution's message tree tell one checkpoint apart from another.

When you open the Replay dialog for an execution, "Restart from Origin" is always the first option. If its flow contains at least one Mark Replay Point node that the message actually passed through during that specific execution, each recorded checkpoint appears as an additional option below it, most recent selected by default - adding the node later doesn't retroactively make older, already-recorded executions offer a checkpoint; they still restart from scratch until re-run. A Mark Auto Replay Point node's own recorded checkpoints (see "Automatic Replay" below) show up here too, tagged auto - it's exactly as safe a manual reset location as a Mark Replay Point one, so there's no need for a redundant Mark Replay Point node right next to it. Picking one of these raises a second, follow-up question before actually resuming: reset the automatic retry count, or keep it? Resetting (the default, and the only behavior every other kind of replay has ever had) gives the resumed execution a full fresh budget of "Max attempts" again. Keeping it instead has the resumed execution inherit the checkpoint's own current attempt count - useful when you're manually continuing the same incident rather than treating the intervention as a brand-new failure chain.

Whichever you pick, the resume target - the flow's true origin (found by following an already-replayed execution's own history back to whichever execution a real inject/http in node actually began - so restart keeps working correctly even many replays deep) for a restart, or the checkpoint node itself for a checkpoint resume - is re-triggered following the flow's current wiring, not a wiring snapshot from whenever the original execution ran. If that node no longer exists, or currently has no outgoing connection at all, the tab reports that clearly rather than guessing at a substitute.

Because a checkpoint node genuinely runs again as part of the new execution, its own output is itself a fresh, valid checkpoint - a resumed execution can be resumed again from the same checkpoint, any number of times, if the retry fails too. That seed message is flagged with a replayed from here badge (or restarted from here for a restart) in the message tree, and the execution's metadata panel shows "Replayed From"/ "Replayed As" links to jump between an execution and whatever it was resumed from or into.

Checkpoints downstream of a Split

A node downstream of a Split - and everything until its matching Join - runs once per part, so a checkpoint there can have several recorded messages for the same execution. The Replay dialog groups those parts together, colored consistently (the same color-hashing the message tree's carousel boxes use, so a repeated node's identity is recognizable in both places), and shows a checkbox per part - any number of them from 1 up to all, not just "all or exactly one" - all checked by default, with "All"/"None" links for convenience.

Which parts actually make sense to replay is a judgment call the dialog leaves to you: each part still carries its original msg.parts metadata unchanged, and a downstream Join relies on that to know how many parts to wait for. Resuming from fewer than all of them will typically leave it waiting forever for the rest - unless that's specifically what you want, e.g. deliberately narrowing in on one or two failing parts for debugging, where Join never completing is expected and fine.

Debugging: resume from any node (unsafe)

Separately from Mark Replay Point, an operator can enable execHistoryUnsafeReplay: true in settings.js to reveal a collapsed "Debugging: resume from any node" section in the Replay dialog, listing every message the execution recorded - not just ones flagged as a sanctioned checkpoint. Picking one resumes from it exactly like a normal checkpoint would. This is deliberately unsafe and disabled by default: it bypasses the whole point of Mark Replay Point, which is forcing a considered decision about where a retry is actually safe. Use it for debugging a specific failure, not as a routine way to retry things. Messages resumed this way are flagged unsafe debug resume in the message tree, and deliberately do not count as a sanctioned checkpoint themselves - resuming from one again still requires debug mode, it doesn't retroactively become safe.

Automatic Replay

Mark Auto Replay Point is a second checkpoint node, alongside Mark Replay Point: it marks the same kind of safe-to-resume-from spot, but instead of waiting for a person to click Replay, it triggers the resume itself automatically the moment the execution fails somewhere downstream - up to a configured number of attempts, with a configurable delay strategy (immediate, fixed, or exponential backoff with jitter) between them. It's a bigger decision than a manual checkpoint: place it only where you're confident it's safe for the flow to retry itself, possibly several times, completely unattended.

Executions produced this way carry replayMode: auto, shown as auto-retried in the metadata panel, and the seed message that re-entered the flow is flagged auto-retried from here in the message tree - the same "Replayed From"/"Replayed As" links the manual checkpoint flow uses still work here to jump between an execution and whatever it was automatically resumed from or into.

A pending automatic retry is durably recorded, not just held in memory - if Node-RED restarts while one is waiting, it's picked back up and still fires once the flow is running again, instead of silently disappearing.

Once the node's configured maximum attempts is reached and the last one has also failed, no further automatic retry happens - that execution is flagged retries exhausted in the Executions list either way. The node's When exhausted setting decides what happens in addition to that: Throw error (the default) raises it via node.error(), catchable with a Catch node, and creates nothing new - deliberately the default, since a second output nobody wired up would otherwise leave a brand-new tracked execution stuck RUNNING forever (see "When is an execution marked COMPLETED?" above). Separate output instead adds a second output that fires exactly once, carrying the last failed payload plus the recorded error, as a new, fully tracked execution (replayMode: auto-exhausted), tagged automatic replay failed rather than the generic replay badge - it's the retry mechanism giving up, not another attempt - wire it to an alert, a dead-letter path, or a Mark Execution Complete node so it actually terminates.

Like Mark Replay Point, a checkpoint placed downstream of a Split always resumes all of that execution's recorded parts together - retrying only the one part that actually failed isn't supported yet, since it would need a persistent, package-owned Join this package doesn't have. This node doesn't replace Restart from Origin or Mark Replay Point either; all three coexist, and manually replaying an execution resets its automatic attempt count back to zero for whatever happens next. This node's own checkpoint is also a valid manual reset location (see "Replay" above) - no need for a separate Mark Replay Point node right next to it just to be able to manually jump back once whatever was flaky is working again.

Grouping Replay/Retry Chains

Every replay - restart, checkpoint, debug, or automatic - creates a brand new, independently tracked execution. Left ungrouped, a flow that fails and gets retried a few times before succeeding shows up as several separate rows in the Executions list, which gets noisy fast, especially with Mark Auto Replay Point in the mix.

The Group replay chains toggle above the Executions list (on by default) instead shows one row per chain - the original execution plus everything it eventually led to, however many replay generations deep. The row's Execution ID is the chain's root (the same execution "Restart from Origin" would restart from); its own Tags column carries a replay badge and/or retries exhausted if any member of the chain used up its automatic retry budget; its Status is the last execution's status, so a chain that eventually succeeds shows as COMPLETED even if earlier attempts failed; its Flow-Duration spans from the first execution's first message to the last execution's completion. View/Replay act on the chain's latest execution - its current state - and the detail view's existing "Replayed From"/"Replayed As" links still show the full chain from there.

Turning the toggle off ungroups the entire list, which is more disruptive than wanting to look closely at just one chain. Instead, any grouped row with more than one execution gets a large expand arrow (▸) next to its id - every other row (a chain with only one execution, or a non-oldest member inside an already-expanded chain) shows a plain dot (•) in the same spot instead, purely so the id column stays aligned. Clicking the arrow swaps that one summary row for its actual member executions, oldest at the top, newest at the bottom, each shown exactly as it would be in the ungrouped view. The arrow moves to the top (oldest) row and now collapses the chain back to its one summary row.

Deep Search

The Deep Search tab searches the actual content of every recorded message across all executions - not just the execution ID or flow name the Executions tab searches by. It's disabled by default; enable it by setting execHistoryDeepSearch: true in settings.js. It's opt-in because, unlike the rest of this dashboard, a search has no index to fall back on - it scans message content directly, so its cost scales with how much history you've accumulated.

A search is a literal, case-insensitive substring match against every message's payload values (not its JSON keys/structure), so searching for part of a string buried anywhere in a payload - an order ID, an error code, a customer name - will find it, without needing to know which field it lives in. Results are grouped one row per execution, even if the term appears in several of its messages, with a short snippet shown inline. Clicking a result opens the same detail view as the Executions tab, already scrolled to and briefly highlighting the exact message that matched (jumping straight to it even if it's deep inside a collapsed branch or a multi-part Split/Join carousel).

When an execution matches more than once, the "Jump to first/last match" control decides which one the snippet and the deep-link refer to: first (the default) is the earliest matching message chronologically - usually where the searched-for content actually entered the flow; last is the most recent one - usually closer to the outcome. Switching it re-runs the current search.

A search scans at most 5000 matching messages (newest first) before giving up and reporting the results found so far - a safety valve against a very common term turning one search into an unbounded scan. If you hit that limit regularly, it's a sign either the search term needs to be more specific, or your message volume has outgrown a plain regex scan (at which point a dedicated search backend, e.g. Elasticsearch, would be the next step - not something this dashboard implements today).

Other design decisions

  • No node placement required for tracking itself. It's global runtime instrumentation (RED.hooks), so every flow is covered automatically the moment a database is configured. The only node this package ships, Mark Execution Complete, is a deliberately dumb pass-through marker - it carries no configuration of its own beyond a name, and exists solely to give non-HTTP flows a COMPLETED signal to reach, nothing more.
  • A failed node's message is flagged, not hidden. The message a node was processing when it called done(err) is still recorded like any other output entry, just flagged isError: true - so the dashboard's message tree shows exactly where things went wrong, alongside the execution-level error details (node, message, stack trace) shown above.
  • MongoDB via a pluggable adapter. Storage goes through an abstract DatabaseAdapter class; only a MongoDB implementation exists today, but the interface is designed so a Postgres/file-based/etc. adapter could be swapped in later without touching the tracking logic.
  • Cleanup is manual only. The Delete dropdown (30d/7d/today/all) is the only way to remove old executions right now - there's no scheduled retention job enforcing the node's configured retention period yet.
  • Vanilla JS dashboard, no framework. This page is static HTML/CSS/JS served directly by the node (no React/Vue, no dependency on Node-RED's own editor framework, and deliberately no express dependency, since this package may be installed outside Node-RED's own node_modules resolution path).
